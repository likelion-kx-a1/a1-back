# A1팀 GeNova 배포 이전 인수인계

> 대상 시스템: GeNova AI 이미지·영상 생성 플랫폼<br>
> 대상 저장소: `a1-back`, `a1-front-2`<br>
> 목적: 개인·프로젝트 AWS 및 Vercel 환경에서 운영 중인 서비스를 인수 회사 소유 환경으로 안전하게 재구축하고 데이터와 운영 권한을 이전한다.

## 0. 문서 사용 원칙

이 문서는 AWS 계정 자체를 넘기는 절차가 아니라, 인수 회사의 신규 AWS 계정에 인프라를 재구축하고 필요한 데이터만 안전하게 이전하는 절차를 설명한다.

다음 정보는 이 문서나 Git 저장소에 기록하지 않는다.

- DB 비밀번호 원문
- JWT Secret
- OpenAI·Anthropic·fal.ai API Key
- SMTP 비밀번호
- AWS Access Key·Secret Access Key
- 개인용 SSH Private Key

비밀값은 인수 회사가 새로 발급하여 자사 AWS Systems Manager Parameter Store 또는 Secrets Manager에 등록하는 것을 원칙으로 한다.

## 1. 서비스 요약

GeNova는 사용자가 텍스트와 참조 이미지를 이용해 AI 이미지·영상을 생성하고, 이미지에서 역프롬프트를 추출하며, 결과를 프로젝트·채팅·보관함 단위로 관리하는 서비스다.

주요 기능은 다음과 같다.

- 사용자 회원가입, 이메일 인증, 관리자 승인
- JWT 기반 로그인과 인증 세션
- OpenAI 기반 이미지 생성·편집
- Seedance·Kling 기반 영상 생성
- Claude 기반 프롬프트 보정
- 이미지 분석 기반 역프롬프트 생성
- 비동기 Generation Job과 Scheduler
- SSE와 Polling을 결합한 생성 완료 복구
- 프로젝트·채팅·생성 에셋 이력
- 프로젝트 보관함, 폴더, 저장·다운로드
- 생성 성공·실패 알림

## 5. Backend CI/CD

### 5.1 CI

Backend GitHub Actions `ci.yml`은 Pull Request와 `main` Push에서 실행된다.

```text
Checkout
  -> Java 21 설정
  -> ./gradlew clean test
  -> docker build -t a1-back:test .
```

### 5.2 Production Deploy

Backend CI가 `main`에서 성공하면 `deploy.yml`이 실행된다.

```text
Backend CI 성공
  -> AWS Credential 설정
  -> ECR 로그인
  -> Docker Image Build
  -> Commit SHA Tag + latest Push
  -> AWS Systems Manager Run Command
  -> EC2에서 deploy.sh 실행
  -> Parameter Store 값 조회
  -> Redis 준비
  -> Backend Container 교체
  -> /actuator/health 확인
```

### 5.3 GitHub Actions Secrets

| Secret | 용도 | 이전 정책 |
|---|---|---|
| `AWS_ACCESS_KEY_ID` | ECR Push 및 SSM 명령 | 인수 회사 IAM Credential로 교체 |
| `AWS_SECRET_ACCESS_KEY` | AWS 인증 | 인수 회사에서 새로 발급, 기존 값 전달 금지 |

장기적으로는 GitHub Actions OIDC를 적용하여 장기 Access Key를 제거하는 것을 권장한다.

### 5.4 배포 고정값

`deploy.yml`과 `deploy.sh`에는 현재 계정 정보가 포함되어 있으므로 이전 시 변경해야 한다.

```text
AWS_ACCOUNT_ID=310971189070
AWS_REGION=ap-northeast-2
ECR_REPOSITORY=a1-back-prod
EC2_NAME_TAG=a1-back-prod
```

대상 회사 계정 ID와 자원명으로 교체한 후 배포한다.

| `/config/a1-back/FAL-API` | SecureString | fal.ai Key | 회사 소유 Key 발급 |

Standard Parameter는 계정 간 소유권 이전 대상이 아니므로 대상 회사 계정에 같은 경로로 새로 생성한다. SecureString 원문을 문서로 전달하지 않는다.

## 7. RDS 인수 절차

### 7.1 원본 계정 담당자 작업

1. 수동 Snapshot이 `사용 가능`인지 확인한다.
2. Customer Managed KMS Key 암호화 사본이 `사용 가능`인지 확인한다.
3. 실제 인수 회사 AWS 계정 ID를 전달받는다.
4. KMS Key 정책에 실제 회사 계정 ID를 추가한다.
5. 암호화 Snapshot을 해당 계정에 비공개 공유한다.
6. 대상 회사가 자기 계정으로 Snapshot을 복사할 때까지 KMS Key와 Snapshot을 유지한다.

### 7.2 인수 회사 작업

1. AWS 콘솔 리전을 `ap-northeast-2`로 선택한다.
2. RDS → Snapshots → Shared with me에서 공유 Snapshot을 확인한다.
3. 인수 회사 소유 Customer Managed KMS Key를 생성한다.
4. 공유 Snapshot을 인수 회사 KMS Key로 복사한다.
5. 복사본 ARN에 인수 회사 AWS 계정 ID가 표시되는지 확인한다.
6. 대상 VPC, DB Subnet Group, Security Group을 선택하여 RDS를 복원한다.
7. Public Access를 비활성화한다.
8. PostgreSQL 5432는 대상 Backend EC2 Security Group에서만 허용한다.
9. 자동 백업을 최소 7일로 설정한다.
10. 삭제 방지를 활성화한다.
11. 새 RDS Endpoint와 Credential을 Parameter Store에 등록한다.

### 7.3 RDS 인수 완료 기준

- 인수 회사 계정 소유 Snapshot 존재
- 인수 회사 KMS Key로 암호화
- 대상 RDS 상태 `사용 가능`
- Backend에서 DB 연결 성공
- Flyway Migration 검증 성공
- 과거 사용자·프로젝트·채팅·에셋 조회 성공
- 자동 백업 7일 이상 및 PITR 활성화

## 8. S3 인수 절차

### 8.1 원본 Bucket

```text
likelion-kx-storage-2026-310971189070-ap-northeast-2-an
```

원본 계정 담당자는 다음을 기록한다.

- 리전
- Versioning 상태
- 기본 암호화 방식
- Object Ownership
- 전체 Object 개수와 크기
- 주요 Prefix
- Lifecycle Rule
- Bucket Policy
- CORS 설정

### 8.2 인수 회사 작업

1. 인수 회사 계정에 새 S3 Bucket을 생성한다.
2. Versioning을 활성화한다.
3. 기본 암호화를 활성화한다.
4. Object Ownership은 Bucket owner enforced를 권장한다.
5. 원본 계정과 Cross-account Replication 권한을 구성한다.
6. 기존 객체는 S3 Batch Replication 또는 검증된 Copy 작업으로 이전한다.
7. 전환 직전에 최종 증분 동기화를 수행한다.
8. 대상 Bucket 이름을 Parameter Store `AWS_S3_BUCKET`에 등록한다.

### 8.3 S3 완료 기준

- 원본과 대상 Object 수 비교
- 원본과 대상 전체 크기 비교
- 최근 이미지 10개 표시·다운로드
- 최근 영상 10개 재생·다운로드
- DB `asset_files.storage_path`에 대응하는 Object 확인
- DB `saved_asset_files.storage_path`에 대응하는 Object 확인
- DB `chat_message_files.storage_path`에 대응하는 Object 확인

RDS만 이전하고 S3를 이전하지 않으면 메타데이터는 존재하지만 실제 이미지·영상이 없는 상태가 된다.

## 9. EC2·IAM·ECR 인수 절차

### 9.1 권장 이전 방식

현재 Backend는 Docker로 배포되므로 기존 EC2 AMI를 장기 운영 기반으로 넘기기보다 인수 회사 계정에 EC2를 새로 구성하고 Git Repository에서 Image를 다시 빌드하는 방식을 권장한다.

### 9.2 인수 회사 생성 자원

| 자원 | 권장 이름 |
|---|---|
| EC2 Name Tag | `a1-back-prod` |
| ECR Repository | `a1-back-prod` |
| EC2 IAM Role | `a1-back-ec2-role` |
| Backend Container | `a1-backend` |
| Redis Container | `a1-redis` |
| Docker Network | `a1-network` |

### 9.3 EC2 IAM Role 최소 권한

- 대상 ECR Image Pull
- 대상 S3 Bucket의 필요한 Object Read·Write
- `/config/a1-back/*` Parameter Read
- SecureString용 KMS Decrypt
- Amazon SSM Managed Instance
- 필요한 CloudWatch Logs 권한

현재 원본 역할의 `AmazonS3FullAccess`는 대상 환경에서 Bucket 단위 최소 권한으로 축소한다.

### 9.4 Network

| 대상 | 포트 | Source |
|---|---:|---|
| Backend HTTPS | 443 | 사용자 또는 Load Balancer |
| HTTP Redirect | 80 | 필요 시 사용자 |
| Spring Boot | 8080 | EC2 Loopback 또는 Reverse Proxy만 |
| PostgreSQL | 5432 | Backend EC2 Security Group만 |
| SSH | 22 | 원칙적으로 닫고 SSM 사용 |

EC2의 IMDSv2를 활성화하고 Docker Bridge Network 사용을 위해 HTTP PUT Response Hop Limit을 `2`로 설정한다.

6. Backend 검증 완료 후 Production Domain을 전환한다.

### 10.3 Frontend CI

현재 GitHub Actions는 디자인 토큰 관련 변경 시 다음 검사를 수행한다.

```text
npm ci
  -> npm run tokens:build
  -> 생성 파일 Git Diff 확인
```

인수 후 전체 `npm run lint`와 `npm run build`를 필수 CI로 추가하는 것을 권장한다.

## 11. DNS·TLS·CORS

Backend Domain이 변경되면 다음을 함께 갱신한다.

- DNS A·AAAA·CNAME Record
- 대상 인증서 또는 TLS 설정
- Vercel `NEXT_PUBLIC_API_BASE_URL`
- Backend CORS Allowed Origin
- SSE Endpoint
- 외부 Webhook URL이 있다면 해당 URL

전환 최소 하루 전에 DNS TTL을 `300초` 수준으로 낮추고, 대상 환경 검증 후 DNS를 변경한다.

## 12. 최종 Cutover 순서

1. 사용자에게 점검 시간을 공지한다.
2. Frontend의 생성·저장 요청을 일시 중단한다.
3. 진행 중 Generation Job이 없는지 확인한다.
4. 원본 RDS 최종 Snapshot을 생성한다.
5. S3 최종 증분 동기화를 수행한다.
6. 대상 RDS·S3 데이터 정합성을 확인한다.
7. 대상 Backend를 시작한다.
8. `/actuator/health`가 `UP`인지 확인한다.
9. 대상 Frontend 환경변수를 변경하고 배포한다.
10. DNS를 대상 Backend로 변경한다.
11. 사용자 시나리오를 검증한다.
12. 기존 환경은 즉시 삭제하지 않고 합의된 안정화 기간 동안 유지한다.

전환 시 가능하면 결과가 `0건`이어야 한다.

## 13. 데이터 정합성 검증

### 13.1 주요 테이블 건수

원본과 대상 DB에서 동일하게 실행하여 비교한다.

```sql
SELECT 'users' AS table_name, COUNT(*) FROM users
UNION ALL SELECT 'projects', COUNT(*) FROM projects
UNION ALL SELECT 'chats', COUNT(*) FROM chats
UNION ALL SELECT 'chat_messages', COUNT(*) FROM chat_messages
UNION ALL SELECT 'generation_jobs', COUNT(*) FROM generation_jobs
UNION ALL SELECT 'generated_assets', COUNT(*) FROM generated_assets
UNION ALL SELECT 'asset_files', COUNT(*) FROM asset_files
UNION ALL SELECT 'saved_assets', COUNT(*) FROM saved_assets
UNION ALL SELECT 'saved_asset_files', COUNT(*) FROM saved_asset_files
UNION ALL SELECT 'notifications', COUNT(*) FROM notifications;
```

### 13.2 완료됐지만 에셋이 없는 Job

```sql
SELECT gj.id, gj.chat_id, gj.status, gj.completed_at
FROM generation_jobs gj
LEFT JOIN generated_assets ga
  ON ga.generation_job_id = gj.id
 AND ga.deleted_at IS NULL
WHERE gj.status = 'COMPLETED'
  AND ga.id IS NULL;
```

정상 기대값은 `0건`이다.

### 13.3 파일이 없는 에셋

```sql
SELECT ga.id, ga.chat_id, ga.asset_type, ga.created_at
FROM generated_assets ga
LEFT JOIN asset_files af ON af.generated_asset_id = ga.id
WHERE ga.deleted_at IS NULL
GROUP BY ga.id
HAVING COUNT(af.id) = 0;
```

### 13.4 프로젝트 보관함 누락

```sql
SELECT p.id, p.user_id, p.name
FROM projects p
LEFT JOIN library_projects lp
  ON lp.source_project_id = p.id
 AND lp.user_id = p.user_id
 AND lp.status = 'ACTIVE'
WHERE p.status = 'ACTIVE'
  AND p.deleted_at IS NULL
  AND lp.id IS NULL;
```

pandoc A1_배포_이전_인수인계.md \
